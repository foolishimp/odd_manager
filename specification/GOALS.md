# Goals

**Status**: Active
**Date**: 2026-07-11
**Derived From**: `specification/INTENT.md`, `specification/PRODUCT.md`

## Position

Goals focus one bounded wave of work.

They are narrower than intent and shorter-lived than product definition.

They keep the current observation recovery and developer-control repricing work
oriented without turning temporary implementation choices into accidental law.

## Current Goals

### G-001 - Establish the admitted ABG/GTL system observation contract

Make ABG/GTL system truth the manager-owned observation core before any
domain-specific overlay is applied.

**Orients**:
- ABG runtime event truth and replay-derived projections
- versioned ABG/GTL system ledgers, catalogs, proofs, and event digests
- registry entries, graph-function selections, node-type satisfaction, payload
  facts, and construction-action catalog entries
- explicit unsupported-domain state when a domain overlay is absent
- one Project observation topology spanning source authority, `.ai-workspace`,
  admitted run roots, and their proof carriers

### G-002 - Keep domain UI packs separate from the core system projection

Keep manager-owned GTL/ABG pages cross-domain while admitting domain-specific
surfaces only through compatible domain UI packs.

**Orients**:
- core runtime, history, provenance, evidence, and traceability pages
- explicit compatibility state for `odd_glc` and future `odd_*` packs
- no domain package redefining ABG run, graph-call, frame, continuation, or
  event truth

### G-003 - Preserve delivery entry lenses as domain overlays

Preserve requirements-first and process-first entry lenses without making their
current `odd_sdlc` shape permanent manager ontology.

**Orients**:
- `Requirements View` over compatible domain requirement and proof overlays
- `Process View` over ABG system projection plus compatible domain process
  overlays
- honest absence or incompatibility state where a selected project lacks a
  supported domain pack

### G-004 - Keep the manager workspace free of legacy local odd_sdlc runtime authority

Prevent the manager source project from being defined by the removed
workspace-local `odd_sdlc` Python runtime install or its generated local
read models.

**Orients**:
- no active runtime contract under `.genesis/odd_sdlc/`
- no live manager authority from `.ai-workspace/runtime/odd_sdlc-*`
- local bootstrap text names `odd_manager` as the product boundary
- observed `odd_sdlc` projects remain external managed products, not the
  manager workspace runtime

### G-005 - Recover generic run operations without restoring odd_sdlc coupling

Recover the operator capabilities formerly presented by Process Navigator as
generic projections over admitted Project, ABG/GTL, run, event, proof, and
artifact carriers.

**Orients**:
- runtime activity, attempts, feedback, graph and function selection
- asset materialization, diagnostics, assurance, events, stages, transcripts,
  artifacts, and runtime targeting
- explicit source references and honest unavailable states
- typed UX state, messages, commands, ingress validation, replay, and bounded
  live refresh
- no `odd_sdlc` runtime, query adapter, carrier, or fixed process taxonomy

### G-006 - Establish the multi-Project developer build-control loop

Make the developer managing multiple Spec Method and ODD-governed Projects the
first primary persona. Organize the product around moving selected Project
revisions from governed specification to evidence-backed, gate-complete build
outcomes.

**Orients**:
- one portfolio-level view of Project revision, readiness, build, assurance,
  freshness, participant, and attention posture
- one goal-oriented Project Workbench for `Review -> Tune -> Build -> Assure`
- attributable and validated specification proposals with explicit acceptance
  or rejection
- typed build requests over published semantic carriers rather than hidden
  shell commands
- bounded concurrent process supervision correlated to ABG-owned runs
- required-versus-delivered gate and asset assurance with explicit repair,
  escalation, and lawful re-entry
- AI Workspace and Run Inspector retained as supporting observation and
  forensic capabilities rather than the product's end goal

### G-007 - Establish modular capability boundaries before functional MVPs

Create the structural capability foundation that lets each major developer
capability iterate independently while preserving one integrated product and
one shared world model.

**Orients**:
- explicit module ownership for Build Portfolio, Project Workbench,
  Specification Proposal, Build Control, Assurance and Attention, and Run
  Observation
- STDO-UX State, Msg, Update, Cmd, Sub, ingress, view, and replay surfaces per
  capability
- shared Context, navigation, command correlation, effect membrane, source
  references, and evidence contracts
- no capability-to-capability internal state mutation or hidden orchestration
- one structural foundation wave before portfolio, proposal, single-build,
  concurrent-build, and assurance MVP iterations
- preservation of existing Project deep links and run observation through the
  modular host boundary
